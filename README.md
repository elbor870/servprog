## 📌 1. Почему нельзя выполнять долгие задачи в теле HTTP-запроса?

Выполнение тяжелых операций внутри эндпоинта — это антипаттерн, который ведёт к деградации всего веб-приложения.

| Проблема | Описание |
|----------|----------|
| **Тайм-ауты** | Веб-серверы (Nginx, Gunicorn) и браузеры имеют жесткие лимиты ожидания (30–60 сек.). Генерация PDF или парсинг сайта занимают минуты → пользователь получает `504 Gateway Timeout`. |
| **Блокировка воркеров** | Синхронные воркеры (например, Gunicorn) имеют ограниченный пул. Если 10 воркеров заняты генерацией отчетов, остальные запросы (даже легкие) встают в очередь или отбрасываются. |
| **Утечки памяти (OOM)** | Библиотеки для PDF и парсинга потребляют много RAM. В рамках HTTP-запроса сложно контролировать сборку мусора, что часто приводит к падению сервера. |
| **Отсутствие устойчивости** | При сбое SMTP-сервера или сети письмо теряется навсегда. В фоновой задаче мы можем настроить автоматические повторные попытки (retry). |

## 📌 2. Брокеры сообщений: RabbitMQ, Redis, Kafka. Концептуальная разница

Брокер — это посредник между вашим API и исполнителями (воркерами). У каждого брокера своя философия.

| Характеристика | RabbitMQ (AMQP) | Redis (как брокер) | Apache Kafka |
|----------------|-----------------|---------------------|--------------|
| **Модель** | Умный брокер, глупый потребитель. Очереди + обменники + маршрутизация по ключам. | Глупый брокер, умный потребитель. Простой список (LPUSH/RPOP). | Распределенный лог-коммит. Сообщения хранятся постоянно в партициях. |
| **Надежность** | Высокая. Подтверждения (ACK), персистентность на диск, Dead Letter Exchange. | Низкая. Хранение в RAM. При перезагрузке Redis все необработанные задачи теряются. | Очень высокая. Репликация, хранение на диске, возможность повторного чтения. |
| **Скорость** | Средняя (за счет гарантий). | Очень высокая (In-Memory). | Высокая, но с задержкой на запись в диск. |
| **Удаление сообщений** | Удаляется после подтверждения воркером (ACK). | Удаляется после `RPOP`. | Не удаляется. Потребитель хранит оффсет (смещение). |
| **Сценарий** | Классические очереди задач (Celery). Важна доставка каждого письма. | Простые проекты, где потеря задачи не критична (кеширование, лёгкие уведомления). | Потоковая обработка, Event Sourcing, аналитика, Big Data. |

**Вывод:**  
- **RabbitMQ** — для надёжной доставки и сложной маршрутизации.  
- **Redis** — для скорости и простоты в небольших проектах.  
- **Kafka** — для огромных потоков данных и событийных архитектур.

## 📌 3. Архитектура Celery и альтернативы в Python

### 🧩 Архитектура Celery

Celery состоит из трёх основных компонентов:

1. **Broker (Брокер)** — хранит задачи (RabbitMQ / Redis).
2. **Worker (Воркер)** — процессы, которые извлекают и выполняют задачи.
3. **Backend (Хранилище результатов)** — опционально, сохраняет статус и результат (Redis, PostgreSQL, Memcached).

**Жизненный цикл задачи в Celery:**

sequenceDiagram
    participant Client as API / HTTP
    participant Broker as Брокер (Rabbit/Redis)
    participant Worker as Celery Worker
    participant Backend as Backend (результат)

    Client->>Broker: 1. send_email.delay() → task_id
    Broker-->>Client: 2. Возвращает task_id (202 Accepted)
    Worker->>Broker: 3. Забирает задачу
    Worker->>Worker: 4. Выполняет (отправка email, PDF)
    Worker->>Backend: 5. Сохраняет результат / статус
    Client->>Backend: 6. Опрашивает статус по task_id
    Backend-->>Client: 7. Возвращает результат

## 📌 Вопрос 4. Что такое идемпотентность фоновых задач и как обрабатывать "отравленные" сообщения (poison pills)?
### 🔁 Идемпотентность фоновых задач

Идемпотентность — свойство операции, при котором её повторное выполнение даёт тот же результат, что и однократное.

Почему это важно?
В распределенных системах сообщения могут быть доставлены дважды:

    Воркер успел выполнить задачу, но не отправил ACK (подтверждение) брокеру из-за сетевого сбоя.

    Брокер переотправил задачу другому воркеру.

Как реализовать идемпотентность:
Способ	Пример
Использовать уникальный task_id	Проверять в БД, выполнялась ли уже задача с таким ID.
Абсолютные значения вместо инкрементов	Вместо UPDATE users SET balance = balance + 100 использовать UPDATE users SET balance = 100 WHERE user_id = X AND balance != 100.
Вести таблицу выполненных задач	Создать таблицу task_log с полями task_id, status, created_at. Перед выполнением проверять, есть ли запись с status='SUCCESS'.
Использовать оптимистичную блокировку	Добавить версию записи (version) и обновлять только если версия совпадает.
☠️ "Отравленные" сообщения (Poison Pills)

Poison Pill — это сообщение, которое воркер не может обработать из-за:

    Невалидного JSON или XML.

    Отсутствия обязательных полей.

    Данных, вызывающих исключение (деление на ноль, обращение к несуществующему файлу).

    Битых данных после обновления схемы (breaking changes).

🛡️ Стратегия обработки Poison Pills
Этап	Действие
1. Перехват исключений	Оборачиваем выполнение задачи в try/except, чтобы воркер не падал.
2. Логирование ошибки	Записываем в лог содержимое сообщения, стек вызовов и контекст.
3. Ограничение Retry	Настраиваем максимальное число повторных попыток (например, 3) с экспоненциальной задержкой (1 сек, 10 сек, 60 сек).
4. Dead Letter Queue (DLQ)	При исчерпании попыток отправляем задачу в специальную очередь для "мёртвых" сообщений. Разработчик анализирует и исправляет баг.
5. Мониторинг и алертинг	Настраиваем оповещение (Slack / Telegram / Email), если количество упавших задач превышает порог.
6. Автоматическое исправление	Для известных ошибок (например, невалидный email) можно исправить данные на лету и повторить.

from celery import Task
import logging

logger = logging.getLogger(__name__)

class BaseTask(Task):
    max_retries = 3
    default_retry_delay = 60  # секунд

    def on_failure(self, exc, task_id, args, kwargs, einfo):
        # Отправляем в DLQ или логируем в специальную таблицу
        logger.error(f"Task {task_id} failed with exception: {exc}")
        logger.error(f"Args: {args}, Kwargs: {kwargs}")
        # Отправляем уведомление в Slack
        send_slack_alert(f"⚠️ Task {task_id} failed: {exc}")

@app.task(base=BaseTask, bind=True)
def send_email(self, to, body):
    try:

    except SMTPException as e:
