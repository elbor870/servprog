Фоновые задачи, очереди и брокеры сообщений

Архитектура микросервисов • Celery • RabbitMQ • Redis

Почему нельзя выполнять долгие задачи в HTTP-запросе?

  • Тайм-ауты — клиент (браузер/nginx) оборвет соединение через 30–60 сек.
  • Блокировка — воркеры веб-сервера (gunicorn/uwsgi) заняты, новые запросы ждут.
  • Утечки памяти — тяжелые операции (PDF, парсинг) могут привести к OOM.
  • Отсутствие retry — при сбое отправки email или генерации PDF всю операцию придется перезапускать вручную.

Брокеры сообщений

RabbitMQ (AMQP) — очередь с маршрутизацией, подтверждениями, dead-letter. Надежность.

Redis — быстрый, in-memory, но есть риск потери данных при сбое. Скорость.

Kafka — распределенный лог (streaming). Хранит сообщения долго, репликация. Масштаб.

Архитектура Celery

Broker (Rabbit/Redis) — хранит задачи. Worker — выполняет. Backend — хранит результаты.

Альтернативы в Python:

  • RQ — легкий, только Redis, простой API.
  • Huey — встроенный планировщик, поддержка SQLite/Redis.
  • Dramatiq — быстрый, с акцентом на надежность, совместим с Rabbit/Redis.

Celery — самый функциональный, но тяжелый. RQ/Huey — для небольших проектов.

Идемпотентность & Poison Pills

Идемпотентность — повторное выполнение задачи не меняет результат (например, обновление статуса заказа по ID).

Poison pill — сообщение, которое воркер не может обработать (битые данные, невалидный JSON).

  • Решение: оборачивать выполнение в try/except, логировать ошибку, отправлять в dead-letter queue.
  • Retry с экспоненциальной задержкой (не более N попыток).
  • Хранить состояние задачи (pending, retry, failed, success).

Как бороться с "отравленными" сообщениями?

Обнаружение

Отлавливаем Exception, проверяем структуру данных, таймауты.

Стратегия

Dead Letter Exchange (Rabbit) + отдельная очередь для "битых" задач. В Celery: acks_late и reject_on_worker_lost.

Мониторинг

Flower / Prometheus. Отслеживаем количество failed задач, чтобы вовремя исправить код воркера.

Детали жизненного цикла задачи в Celery

  1. Вызов: send_email.delay(to, body) → задача сериализуется (JSON/Pickle) и отправляется в брокер.
  2. Брокер: сохраняет сообщение в очередь (напр. celery). RabbitMQ подтверждает получение.
  3. Worker: постоянно слушает очередь. Захватывает задачу, десериализует, выполняет.
  4. Результат: если задан backend (Redis/DB), воркер сохраняет результат или статус ошибки.
  5. Retry: при ошибке воркер может повторно отправить задачу в брокер с задержкой (countdown).
  6. ACK: после успешного выполнения воркер отправляет ack брокеру, сообщение удаляется из очереди.

Для длительных задач используют acks_late=True — подтверждение только после выполнения (защита от потери задачи при падении воркера).
